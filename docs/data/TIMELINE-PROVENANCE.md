# Timeline Provenance — why `occurred_at` is NULL

**Status:** frozen rule. P1-C. No dates may be invented.

## What exists

`data/master/master.json` carries `timeline[]` — 62 events describing
institution lineage:

| event_type | count | meaning |
|---|---|---|
| `MERGED` | 42 | predecessor absorbed into the named institution |
| `ACQUIRED` | 19 | predecessor acquired by the named institution |
| `RENAMED` | 1 | the institution itself was renamed |

Every event has this shape (real row, `mfi-030`):

```json
{
  "institution_id": "mfi-030",
  "event_type": "MERGED",
  "title": "Aarambha Laghubitta Bittiya Sanstha Ltd.",
  "occurred_at": null,
  "predecessor_id": "hist-aarambha",
  "predecessor_name": "Aarambha Laghubitta Bittiya Sanstha Ltd."
}
```

## The rule: `occurred_at` stays NULL

**All 62 events have `occurred_at: null`.** This is not a defect to fix by
picking dates; it is an accurate statement about what the source recorded.

Why they are null:

1. **The NRB mid-May 2026 BFI list records lineage as facts, not as dates.**
   It tells us *which* entities were absorbed into *which* survivor. It does
   not tell us *when*. The source itself carries no date field for these
   events.
2. **The capture day of the NRB list is itself unknown.** The snapshot is
   labelled "mid-May 2026" (`source_id: nrb-bfi-mid-may-2026`);
   `universeSnapshot.observed_at: 2026-06-20` is a hardcoded *verification*
   date from `build-master.cjs:245`, not a capture date. If the capture day
   is unknown, any per-event date derived from it would be doubly invented.
3. **`build-master.cjs` is dead.** Its inputs (`*_dump.json`) were deleted,
   so no re-run can add dates — and re-running would not help anyway, because
   the inputs contain no dates either.

## What must not happen

- Do **not** backfill `occurred_at` with the NRB snapshot date, the
  verification date (`2026-06-20`), a default (`1900-01-01`), or any other
  placeholder. A wrong date in a lineage record is worse than an honest NULL:
  downstream readers will plan, sort, and cite it.
- Do **not** infer dates from `institutions.operation_date` or from alias
  `last_verified_at`. Those describe different facts on different sources.
- Do **not** regenerate `timeline[]` — `build-master.cjs` cannot run
  (inputs absent), and `master.json` is fingerprinted in
  `data/master/master.sha256`.

## How NULL is handled downstream

| consumer | behaviour |
|---|---|
| `verify-master-integrity.ts` | reports "N events, M with no occurred_at" as a NOTE, never a FAIL |
| `UNIQUE (institution_id, event_type, occurred_at)` | still holds — NULL makes the constraint non-binding for these rows, which the schema already tolerates |
| UI / API | timeline events render without a date; no placeholder date is shown |
| lineage resolution | by **name**, not by date — see below |

## Lineage is resolved by name, not by date

Because events are undated, the way to make lineage usable is the alias
graph, not a date axis:

1. Each `predecessor_name` becomes an `institution_aliases` row with
   `alias_type='FORMER'`, pointing at the surviving `institution_id`.
   Generated by `scripts/build-canonical-former-aliases.ts` into
   `data/master/canonical-former-aliases.json` (62 rows), backfilled into
   `data/durable/store.db` in P1-F.
2. Each old slug becomes a `slug_aliases` row (`old_slug` → `moved_to`),
   generated by `scripts/build-canonical-slug-aliases.ts` into
   `data/master/canonical-slug-aliases.json` (16 rows) and backfilled too.
3. `scripts/verify-master-integrity.ts` checks that every
   `predecessor_name` in `timeline[]` is covered by a canonical FORMER
   alias, and every canonical alias points at a real institution.

So the question "what absorbed Aarambha?" is answerable today
(`mfi-030`, via `FORMER` alias). The question "when?" is honestly
unanswerable until a source that records the date is obtained.

## If a dated source ever appears

Record it as a **new** observation with its own `source_id` and grade; do
not overwrite `occurred_at` on the NRB-derived events. When (and only when)
a Grade A source publishes per-event dates, populate `occurred_at` from that
source and re-run the integrity verifier with `--write` if `master.json`
itself changes.
