## Retry-safety findings (from code inspection)

- Ingestion runs are recorded in `ingestion_runs` with status RUNNING/SUCCESS/FAILED/PARTIAL; partial writes are possible (items_found > 0, items_failed > 0).
- `ingestion_items` are keyed by (run_id, url) UNIQUE, so a re-run creates new item rows per run; assertions are deduplicated by the ingestion adapter (`saveConflict` dedupes rather than removes).
- `data_assertions` carry `source_id`, `source_snapshot_id`, `observed_at`, `confidence`, `verification_status`; provenance is preserved across runs.
- `data_conflicts` are never deleted; resolution is the only mutation path (`resolveConflict` in lib/ingestion/review.ts), and it is not exposed on the repository contract.
- Dry-run/targeted execution: ingestion sources support `enabled` flag and per-source config; the operator CLI (`npm run ops`) is guard-env-gated. No blanket 'rerun all' is recommended.
- External contact: each retry fetches the institution's website (and NRB pages). Respect source access rules and robots; do not crawl aggressively.
- No production data was touched by this audit.

## Limitations

- PARTIAL runs are classified by recorded error type/message only; root cause for some may require re-running (not done here).
- Pilot-stub causes are inferred from null `last_run_at` (ingestion never executed) plus source registration; no run record exists to confirm.
- Retry safety is assessed from code inspection, not execution.
